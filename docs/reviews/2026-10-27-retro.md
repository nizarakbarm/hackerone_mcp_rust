# Retro candidates — 2026-10-27 (Rust port of hackerone-mcp)

Ordered by severity. Each names the evidence from this session.

## 1. No single check command (Automated checks)

**Evidence:** subagents ran hand-rolled `cargo test -p …`, `cargo clippy --workspace …`,
`rustfmt --check` combinations and disagreed about whether tests executed at all — one reported
"`cargo test` under this shell only prints Finished and never spawns the harness" and ran
`target/debug/deps/client-*` directly; another reported a sibling's failing test as fact.

**Fix:** add `scripts/check.sh` (`cargo fmt --all --check` → `cargo clippy --workspace
--all-targets -- -D warnings` → `cargo test --workspace --no-fail-fast`) and make CI call it.
One command, one exit code, quoted verbatim in every subagent brief.

## 2. Spec invariants are not guard tests (Coding standards → check)

**Evidence:** the architecture refactor moved `ProgramScope` construction to `tools/call`, silently
reducing the program-id cache from process lifetime (spec requirement, issue #1) to a single call.
The reviewer did not catch it; the final subagent self-reported it in a `ponytail:` note. Nothing
in the tree failed.

**Fix:** already partially closed — `one_scope_caches_the_program_id_across_tool_calls` now proves
process-lifetime caching. Generalise the rule for the reviewer agent: *every "cached for the
process lifetime / never re-fetched" claim in a spec needs a test that spans two calls.*
Judgement call, so it belongs in the reviewer's brief, not a linter.

## 3. Upstream API facts live only in the vault (Navigation)

**Evidence:** HackerOne rate limits and the `{"errors":[…]}` body shape arrived only after a
41-minute scout run against external docs. Nothing in the repo states them, so the next agent
re-crawls; the README mentions none.

**Fix:** add `docs/hackerone-api.md` (endpoint table, auth, pagination, rate limits, error shape)
and link it from the README and `docs/agents/`; point the reviewer brief at it instead of
re-researching.

## 4. Tracker writes are a slow loop (Tool economy)

**Evidence:** publishing 22 tickets as sub-issues + blocking edges via sequential `gh api` calls
took 197 s; every link required two round trips (create, then resolve database id, then link).

**Fix:** one GraphQL `createIssue` per ticket plus a single `addSubIssue`/dependency batch, or
create blockers first and pass ids forward. Only worth it if we publish >10 tickets again.
