# Retro — v0.2.0 session (2026-10-27)

## 1. Version/tag drift shipped in v0.1.0 and v0.2.0 (Automated checks) — FIXED

`v0.2.0` artifacts reported `hackerone-mcp 0.1.0`: `[workspace.package] version` was never bumped,
and nothing tied the git tag to the crate version. Caught only by downloading and running the
release binary — after the release was published.

Fixed two ways: workspace version bumped to `0.2.0`, and `release.yml` gained a **Tag matches crate
version** step that fails the release when `v<tag>` ≠ the `hackerone-mcp` crate version. Tag
`v0.2.0` and its release were deleted and re-created on the corrected commit; artifact verified
(`0.2.0`, checksum OK).

## 2. Release verification is not in the gate (Automated checks)

Both releases needed a human step — download, untar, run `--version`, `shasum -c`, count advertised
tools — to catch real defects. Nothing in CI does it.

Candidate: a `release-smoke` job on tag that downloads the just-built artifact, runs `--version`,
asserts it equals the tag, and asserts `tools/list` returns the expected tool count. Cheap; catches
exactly the class of bug that reached two releases.

## 3. Wave agents self-report green, and I re-ran anyway (Tool economy)

Every wave ended with "`./scripts/check.sh` clean, N tests". I re-ran the same command each time
(≈30 s each) because the alternative is trusting an unverified claim.

Candidate: leave as is. The re-run is the verification step for a behavioural claim, and it caught
nothing only because the agents were accurate. Do not optimise this away.

## 4. `expect()` reached production via a registry lookup (Coding standards → check)

`ToolName::class()` looked the class up in `WIRED` and `.expect()`ed the invariant. Reviewer caught
it; the fix was an exhaustive `match`, which is what the type system wanted all along.

Candidate: extend the reviewer brief — *"any `.expect()`/`.unwrap()` reachable from a request path is
a finding unless the type system cannot express the invariant"*. Already covered by
`skill://rust-skills` `err-no-unwrap-prod`; the gap was that the reviewer only flagged it after the
fact. No new rule needed; note it in the next reviewer brief.

## 5. Test helper duplication across integration binaries (Coding standards)

Four helpers were copied verbatim into five `tests/*.rs` files — each is its own crate, so sharing
requires `tests/common/mod.rs`, which no rule mentioned.

Candidate: add one line to the reviewer brief: *"integration-test helpers appearing in more than one
`tests/*.rs` belong in `tests/common/mod.rs`."* Mechanical enough that a future lint could catch it.
